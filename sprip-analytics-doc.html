Platform Architecture

SPRIP is a multi-tenant SaaS platform for pharmaceutical companies to measure the return on investment of their HCP (Healthcare Professional) speaker programs. It combines causal inference, machine learning, and financial modeling to answer: did this speaker event actually move prescriptions?

M1 — Propensity Model

M1 HCP Speaker Event Propensity Scoring

Predicts the likelihood that an HCP will be selected as a speaker for future events, based on their prescribing behavior, engagement history, and demographic profile.

Algorithm

Logistic Regression with L2 regularization (C=1.0), solved via L-BFGS. Binary classification: treated (attended/spoke at event) vs. control (did not attend).

Cross-Validation

5-fold Stratified K-Fold to preserve the class imbalance ratio (~17.6% treated) in each fold. Metrics computed per fold and averaged.

Feature Engineering

14 numeric features + 3 encoded categorical features from hcp_event_features.csv:

  • avg_nrx_3m
  • avg_nrx_6m
  • avg_trx_3m
  • avg_trx_6m
  • nrx_trend
  • competitor_trx_avg
  • rep_calls_3m
  • emails_3m
  • samples_3m
  • prior_event_count
  • specialty_topic_match
  • access_index
  • seasonality_index
  • competitor_index
  • segment (encoded)
  • specialty (encoded)
  • region (encoded)

How It Works

1
Data Load — Read HCP event features CSV. Separate features (X) from the binary label (y: treated/control).
2
Encoding — Label-encode categorical columns (segment, specialty, region) to integers.
3
Cross-Validation — 5-fold StratifiedKFold. Each fold trains a LogisticRegression, records AUC-ROC and accuracy.
4
Full Training — Retrain on all data. Generate classification report (precision, recall, F1 per class).
5
Artifact — Serialize the final model to propensity_model.joblib.

M2 — Causal DiD Estimator

M2 Difference-in-Differences Causal Impact

Estimates the Average Treatment Effect on the Treated (ATT) — how much incremental prescription volume a speaker event actually caused, controlling for secular trends.

Algorithm

Difference-in-Differences (DiD) with propensity-score matched pairs. The core assumption: absent the event, treated and control HCPs would have followed parallel prescription trends.

Mathematical Formulation

ATT = E[Y₁(post) - Y₁(pre)] - E[Y₀(post) - Y₀(pre)] Where: Y₁ = Treated group (HCPs who attended/spoke at event) Y₀ = Control group (matched HCPs who did not) pre/post = Relative to the event date Concretely: treated_diff = nrx_post - nrx_pre (for each treated HCP) control_diff = nrx_post - nrx_pre (for each control HCP) ATT = mean(treated_diff) - mean(control_diff)

Statistical Testing

SE = sqrt( var(treated_diff)/n_treated + var(control_diff)/n_control ) t = ATT / SE p = 2 × (1 - CDF_t(|t|, df = n_treated + n_control - 2)) 95% CI = ATT ± t₀.₀₂₅(df) × SE

Procedure

1
Load Matched Pairs — matched_pairs.csv provides pre-computed propensity-matched treated-control HCP pairs.
2
Determine Cutoff — The median event date splits the timeline into pre and post periods.
3
Aggregate NRx — Compute mean monthly NRx for each HCP in pre vs. post periods from hcp_rx_monthly.csv.
4
Calculate ATT — Subtract control group's pre-post difference from treated group's pre-post difference.
5
Inference — Pooled-variance t-test via SciPy stats.t.sf. Produce SE, t-statistic, p-value, and 95% CI.

M3 — Forecast Model

M3 Brand-Level NRx Forecasting

Predicts future monthly NRx volume at the brand level, used for budget planning and ROI projections.

Algorithm

LightGBM gradient boosting (with GradientBoostingRegressor as fallback). Time-series features engineered from historical prescription data.

Feature Engineering

9 engineered features from brand-level monthly aggregates:

  • nrx_lag1 — NRx value, 1 month prior
  • nrx_lag2 — NRx value, 2 months prior
  • nrx_lag3 — NRx value, 3 months prior
  • nrx_roll3 — 3-month rolling mean
  • nrx_roll6 — 6-month rolling mean
  • trx_lag1 — Total Rx, 1 month prior
  • competitor_lag1 — Competitor Rx, 1 month prior
  • trend — Linear trend component (0, 1, 2, ...)
  • month_num — Calendar month (1–12, seasonality)

Plus product_enc: label-encoded brand identifier for multi-brand training.

Train/Test Split

80/20 time-based split (no shuffle) — the test set is always the most recent 20% of months, preserving temporal ordering.

Impact analysis quantifies the causal effect of each speaker event on prescribing behavior.

ROI Calculation

ROI is computed at three levels of aggregation, each building on the one below.

Calculation Hierarchy

flowchart LR
    EVENT["Event ROI"]
    CAMPAIGN["Campaign ROI"]
    BRAND["Brand ROI"]
    EVENT -->|"aggregate by campaign_id"| CAMPAIGN
    CAMPAIGN -->|"aggregate by brand_id"| BRAND

Core Formulas

Revenue per NRx = ₹850 (configurable per brand) Gross Contribution = Incremental NRx × Revenue per NRx Net ROI = Gross Contribution - Total Event Cost Benefit-Cost Ratio (BCR) = Gross Contribution / Total Event Cost

Event-Level ROI

Computed per event from the event's impact analysis and cost data:

event.gross = event.incremental_nrx × 850 event.net_roi = event.gross - event.total_cost event.bcr = event.gross / event.total_cost

Campaign-Level ROI

Aggregated across all events in the campaign:

campaign.total_incremental_nrx = SUM(event.incremental_nrx) for events in campaign campaign.total_cost = SUM(event.total_cost) campaign.gross = campaign.total_incremental_nrx × 850 campaign.net_roi = campaign.gross - campaign.total_cost campaign.avg_bcr = campaign.gross / campaign.total_cost

Brand-Level ROI

Aggregated across all events for the brand. This is the figure shown on the analytics dashboard as "Avg ROI".

Evidence Grading Framework

Every analytical result is assigned an evidence grade — a signal of confidence derived from the statistical properties of the underlying analysis, not from scores or subjective assessment.

GradeCriteriaInterpretation
STRONG p < 0.05 AND n_treated > 20 Statistically significant with adequate sample size. High confidence that the observed effect is real.
MODERATE p < 0.10 Marginally significant. The effect is directionally correct and likely real, but cannot be confirmed at the 5% level.
DIRECTIONAL p ≥ 0.10 or n_treated ≤ 20 Insufficient evidence for statistical claims. The point estimate may still be useful for planning but carries substantial uncertainty.

Design Principles

Evidence is graded from gates, not scores. The grade comes from hard thresholds on p-value and sample size — not from a weighted composite or ML confidence score. This makes the grading transparent and auditable.

Unmeasurable is recorded as absent, not zero. When an event's impact cannot be estimated (insufficient data, no matched controls), the system records a null impact rather than an impact of zero. This prevents diluting portfolio-level averages with false zeros.

Prescriber-grain model output never leaves the analytics schema. Individual HCP prescribing data used to compute impacts stays within the analytics schema. Published results expose only event-level and above aggregates.

Tenant Isolation

Every table has a tenant_id column with a Row-Level Security policy:

SET LOCAL app.tenant_id = '<tenant-uuid>';

This GUC is set at the start of every database transaction. RLS policies filter all reads and writes to the current tenant automatically — application code never needs to add WHERE tenant_id = ... manually.

Security & RBAC

Authorization uses fine-grained permissions, not role checks. Endpoints call require(Permission.EVENT_WRITE), never if role == PHARMA_ADMIN.

Role Permission Matrix

Role Key Grants Notable Restrictions
PLATFORM_ADMINTenant CRUD, health, auditCannot read any customer commercial data
PHARMA_ADMINFull analytical read + all admin + HCP/event writeNo RX_READ — prescriber data is analyst-tier
ANALYTICS_LEADFull analytical read + RX_READ + analysis run + model trainCannot publish results or approve models (separation of duties)
COMPLIANCE_REVIEWERFull analytical read + result publish + model approve + auditCannot produce results — only review and clear them
FINANCE_REVIEWERFull analytical read + assumption write/approveOnly role that can approve financial assumptions
BRAND_MANAGERFull analytical read + event/campaign write within brand scopeScoped to assigned brands via brand_scope
DATA_STEWARDHCP/Rx read-write, identity resolution, mapping, data publishNo analytical writes or model operations
VENDOR_CONTRIBUTORUpload read/write, own data healthBlocked from ALL analytical data (VENDOR_FORBIDDEN set)
EXECUTIVE_VIEWERFull analytical readNo writes anywhere, no export creation

Critical Security Rules

PLATFORM_ADMIN is not a superuser. It cannot read customer data — by design, not by oversight.

Vendor isolation is subtracted, not granted. The VENDOR_FORBIDDEN set is applied at principal construction time. A misconfigured membership cannot leak prescription outcomes to a data supplier.

Sensitive actions require re-authentication. The REAUTH_REQUIRED set (membership changes, financial approvals, result publication, model approval) forces a recent second factor.

Separation of duties. The person who runs an analysis cannot publish it. The person who trains a model cannot approve it. These separations are structural — encoded in the permission matrix, not in endpoint logic.

Glossary of Analytics Terms

Plain-language definitions of every metric shown on the Impact Analysis, ROI Analysis, and Brand Forecast sections of the platform.

Impact Analysis Metrics
TermWhat It Means
ATT
Average Treatment Effect on the Treated		 The average number of extra prescriptions (NRx) each HCP wrote because they attended the event, compared to what they would have written without the event. An ATT of 7.8 means each attending HCP wrote roughly 7.8 more prescriptions than the matched control group.
Incremental NRx The total additional prescriptions attributable to the event across all treated HCPs. Calculated as ATT × n_treated. If ATT = 7.8 and 15 HCPs attended, the event drove roughly 117 additional prescriptions.
p-value The probability that the observed effect could have occurred purely by chance. A p-value of 0.05 means there is a 5% chance the result is a statistical fluke. Lower is better: p < 0.05 is statistically significant, p < 0.10 is marginally significant.
95% Confidence Interval
CI Low / CI High		 The range within which we are 95% confident the true ATT falls. A CI of [3.21, 12.39] means the real effect is very likely between 3.21 and 12.39 additional NRx per HCP. Narrower intervals indicate more precise estimates.
Standard Error (SE) A measure of how uncertain the ATT estimate is. Smaller SE means the estimate is more precise. It accounts for variability in both the treated and control groups. The CI is computed as ATT ± 1.96 × SE.
n_treated The number of HCPs in the treated group — those who attended or spoke at the event. Their prescribing behavior is compared before and after the event.
n_control The number of matched control HCPs — similar professionals who did not attend the event but have comparable prescribing history and demographics. They establish the baseline: what would have happened without the event.
Evidence Grade A confidence label assigned based on statistical thresholds:
  • STRONG — p < 0.05 and more than 20 treated HCPs. High confidence the effect is real.
  • MODERATE — p < 0.10. The effect is likely real but not confirmed at the conventional 5% level.
  • DIRECTIONAL — p ≥ 0.10 or too few treated HCPs. The point estimate suggests a direction but carries substantial uncertainty.
ROI Analysis Metrics
TermWhat It Means
Total Cost The sum of all costs associated with the event: venue rental, speaker honorarium, travel and accommodation, catering, logistics, and any other recorded expenses.
Gross Contribution The revenue generated by the incremental prescriptions. Calculated as Incremental NRx × Revenue per NRx (default ₹850 per prescription). This is the top-line value the event created.
Net ROI The profit (or loss) from the event after subtracting costs: Gross Contribution − Total Cost. A positive Net ROI means the event generated more revenue than it cost.
BCR
Benefit-Cost Ratio		 How many rupees of revenue each rupee spent produced: Gross Contribution / Total Cost. A BCR of 12.7x means the event returned ₹12.70 for every ₹1 spent. BCR > 1 means the event was profitable.
Revenue per NRx The assumed revenue contribution of each incremental prescription. Currently set to ₹850 per NRx, configurable per brand. This bridges the gap from prescription volume to financial value.
Brand Forecast Metrics
TermWhat It Means
Point Estimate The model's best prediction of per-HCP NRx impact for future events. Generated by the LightGBM model (M3) using historical trends, seasonality, and event characteristics.
Prediction Interval
PI Low / PI High		 The 80% range where actual NRx is expected to land. Unlike a confidence interval (which bounds the estimate's center), a prediction interval bounds where the actual future observation will fall — it is wider because it includes both estimation uncertainty and natural variability.
Expected Attendance The predicted number of HCPs who will attend the event, based on historical attendance patterns for similar events. Used to scale the per-HCP forecast to total event impact.
Expected Incremental NRx The predicted total additional prescriptions from the event: Point Estimate × Expected Attendance. This is the forecast equivalent of the impact analysis's Incremental NRx.
Expected Net ROI The projected profit from the event: Expected Incremental NRx × Revenue per NRx − Expected Cost. Helps budget planners decide whether an upcoming event is worth funding.
Mode
MODEL / POOLED		 MODEL means a brand-specific model had enough data to make a direct prediction. POOLED means the model borrowed data from similar brands to improve prediction stability — common for brands with limited event history.
