Machine Learning Documentation

ML Pipeline

Three models that answer the core business question: which HCPs should we invite to speaker programs, and what ROI should we expect?

Models

M1
Propensity
Logistic Regression

Predict likelihood an HCP will respond to a speaker program. Output: P(respond | features) ∈ [0, 1]

M2
Causal DiD
Difference-in-Differences

Estimate causal treatment effect of speaker events on prescribing behaviour. Output: ATT

M3
Forecast
LightGBM Regressor

Predict next-month Rx volume per product for forward-looking ROI projections.

All models train on synthetic data for demo. The same pipeline structure applies to production data without code changes.

M2 — Causal DiD Estimator

Objective: Estimate the causal effect of speaker program participation on HCP prescribing using a Difference-in-Differences design.

Method: Classic two-period DiD with propensity-score matched controls.

Design

  1. Matching — Treated HCPs are propensity-score matched to controls from gold/matched_pairs.csv
  2. Cutoff — Median event date splits the timeline into pre/post periods
  3. Outcome — Average NRx per HCP in each period
  4. Estimand — ATT = (Treatedpost − Treatedpre) − (Controlpost − Controlpre)

Speaker program attendees increased their average NRx by 1.78 scripts/month more than matched controls. The tight CI and p < 0.001 indicate strong statistical significance on this synthetic dataset.

Key Assumptions

  • Parallel trends — Pre-treatment prescribing trends are similar between treated and control groups
  • No spillover — Control HCPs are not indirectly affected by the speaker program
  • Common support — Matched pairs share similar observable characteristics

No persisted artifact — M2 is a statistical estimator. Results are stored in ml.model_versions and ml.model_metrics with lifecycle_state = 'DRAFT'.

Running the Pipeline

Training

# From project root
.venv/Scripts/python scripts/train_models.py
  1. Reads gold/silver-layer CSVs from DATA_EXTRACT/
  2. Trains M1, M2, M3 sequentially
  3. Serialises artifacts to artifacts/models/
  4. Writes metrics JSON alongside artifacts
  5. Records ml.model_specs, ml.model_versions, ml.model_metrics in PostgreSQL

HCP Scoring

# From project root
.venv/Scripts/python scripts/score_hcps.py
  1. Loads trained propensity model from artifacts/models/propensity_model.joblib
  2. Fetches all HCPs from core.hcps (falls back to CSV)
  3. Builds feature vectors from silver-layer CSVs
  4. Generates propensity scores and rankings
  5. Writes to analytics.propensity_scores table (falls back to JSON)

Model Lifecycle

DRAFT
ACTIVE
ARCHIVED
  • DRAFT — Model version created, metrics recorded, not yet serving predictions
  • ACTIVE — Promoted after validation; used by scoring pipeline and API
  • ARCHIVED — Superseded by a newer version; retained for audit trail

Only one version per model_spec can be ACTIVE at a time. M2 stays in DRAFT because it produces statistical estimates rather than deployable predictions.

Production Considerations

Data Quality

  • Input CSVs must pass schema validation before training
  • Missing features are zero-filled (documented per model above)
  • Unknown categories at scoring time default to encoded value 0

Reproducibility

  • All models use random_state=42
  • Training metadata captured in training_summary.json
  • Artifact checksums enable integrity verification

Monitoring

  • Metrics stored in PostgreSQL and exposed via API endpoints
  • Analytics Dashboard displays ROI trends from M2 causal estimates
  • Forecast accuracy tracked by comparing M3 predictions against actual NRx

Retraining

  • Recommended cadence: monthly, after new Rx data ingestion
  • Pipeline is idempotent — rerunning creates new model_versions rows
  • Celery task analytics.refresh_propensity_scores triggers scoring after retraining

Security

  • Training scripts connect via app_rw role with tenant-scoped RLS
  • Production deployments use MinIO/S3 with signed URLs
  • No patient-level data, PII, or ABHI identifiers in training features
  • Propensity scores are tenant-isolated via RLS policies
